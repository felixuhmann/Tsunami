# RVox editor UI checklist (hosted capture vs original evidence)

Capture: `hosted-editor-linux-pluginval.png` (371x357), taken from the exact locally
built module `Tsunami RVox.vst3/Contents/x86_64-linux/Tsunami RVox.so` (before the product was renamed to the targets.json identity "Tsunami Voice")
(sha256 `2d5f17f9f2647ec09e63798c6360764feca9fa83a4e9f8b06de6577e4f3e30f8`), hosted by
pluginval 1.0.4 in-process under Xvfb. Source commit `acbcae6`; the plugin and shared
trees are the same as at `ec03b32`, the commit the module was built from. Receipt:
`hosted-editor-receipt.json`. Log: `hosted-editor-pluginval.log`.

Original evidence (private, not in git): `tsunami-reference/analysis/rvox/ui-reference/`,
including the user guide text (`rvox-manual.txt`) and the guide's Interface page
(`page-3.png`, numbered callouts 1 to 6), plus the 17.1 layout resources used in c642e01.
Nothing from those sources is copied into this repository. Everything in the editor is
painted in code.

This is a manual review only. No numeric fidelity score is given. Status values:
**present**, **partial**, **gap**, **not verified**.

The fader values in the capture are whatever pluginval's Editor Automation (seed 17) had
set at that moment. They are not a chosen preset.

## Features (guide text)

| Feature | Status | Evidence / gap |
|---|---|---|
| Comp + Gain linking by drawing a box around the faders (they then move together) | **present (unit test)** | rvox.editor checks 22 to 26: a box links comp+gain only, the offset is kept, and a background click unlinks. Only user input moves the linked pair (comp and gain keys, gain value entry, drag, wheel, double-click and alt-click reset; checks 24, 43 to 47 and 49; a key press after unlinking moves comp alone, check 26). Host automation and state recall of one linked parameter leave the other unchanged (checks 40, 41, 42, 48). Not exercised in the hosted capture. Linked follower writes are sent inside an editor-opened host gesture (see the next row). |
| Host gestures from fader drags | **present (unit test)** | rvox.editor checks 60 to 62 on all three faders: each drag starts one gesture, and begins and ends stay balanced after a normal release, an editor closed mid-drag, and a repeated press with a duplicate release. These are component events under xvfb, not native-peer input. |
| Host gestures for linked follower faders | **present (unit test)** | rvox.editor checks 80 to 92 with a real `AudioProcessorListener`: with Comp+Gain linked and Gain leading, every Compression change from a drag, an editor closed mid-drag (Gain or Compression leading), a key, a wheel step, double-click and alt-click reset, and value entry arrives inside a host gesture; begins and ends stay balanced, Gate is untouched and the offset is kept. Host automation and state recall while linked write no follower and start no gesture. Each action opens exactly one follower gesture. It stays open for the leader's drag and closes on its drag end (checked before the editor closes) or on editor close; a mutant without the drag-end close fails check 92. Before the fix the drag case logged 3 follower changes with 0 gestures. These are component events under xvfb, not native-peer input. |
| Host gestures for the leader's key and value entry | **present (unit test)** | rvox.editor checks 93 to 96 with the same real `AudioProcessorListener`: an arrow-key step and an edited value label on Gain or Compression, linked or unlinked, each send their own change inside exactly one host gesture. Unlinked, the other fader gets no write and no gesture. Drag, wheel and double-click or alt-click reset still send exactly one gesture (no duplicate). An unhandled key, a modified arrow, an arrow at the range limit or the same value typed differently ("-4.30" after "-4.3") opens no gesture; a mutant without that value check fails check 95. A value entered during a live drag joins its gesture. JUCE sliders do not take keyboard focus by default and the editor does not enable it, so the key path is defensive and is driven here by calling `keyPressed` directly. A key pressed during a live drag joins that drag's gesture instead of nesting one. Before the fix every key and value-entry case logged one unbracketed change with 0 gestures (exit 93). A mutant without the open-drag guard fails check 96. These are component events under xvfb, not native-peer input. |
| Malformed value entry is ignored | **present (unit test)** | JUCE's text parser turns "nan" or "-NaN" into NaN and an overflowing exponent ("1e999") into an infinity. Before the fix such text wrote NaN to the host-visible parameter (and to a linked follower) or jumped the fader to a range limit (rvox.editor exit 98, 24 cases). Now a non-finite parse is rejected before any clamp, gesture or write and the readout returns to the current value. rvox.editor check 98 covers all three value boxes, linked and unlinked: no parameter, gesture or Comp-pill change, and host automation and state recall afterwards stay isolated. A finite non-integral entry (-7.25, linked Comp follows), gate -35.5, and gate "-Infinity" to off still work; "nan" typed with the gate off restores its "-inf" readout. Some odd finite text still follows JUCE's parse (e.g. "1e308" moves to the maximum, a wrapped huge exponent reads as a small one). Other text keeps JUCE's parse (e.g. "abc" reads as 0); this is not general input validation. Direct Label calls under xvfb, not native-peer input. |
| Double-click a value box to type a value | **present (unit test)** | The value labels become editable on double-click. rvox.editor check 19 enters a gain value. Not exercised in the hosted capture. |
| Option/alt-click resets to default | **present (unit test)** | Uses the JUCE slider double-click-return value, which also responds to alt-click by default. rvox.editor checks 20 and 21 check the reset values; check 49 sends an actual alt-click to the linked gain fader. Not exercised in the hosted capture. |
| Click output meter or peak number to reset peak | **partial** | Output peaks: implemented (rvox.editor check 30). Total Compression peak: implemented with the bridge (check 77, see #4). |
| Skins: Light / Dark / Legacy, chosen from the WaveSystem toolbar; the skin persists as the default for new instances | **present (feature) / partial (look)** | A small "Skin" selector in the editor header (top right, 282,10 82x20) offers Light, Dark and Legacy. Light is the existing look and stays the clean-install default. Outside the selector rectangle, the Light editor snapshot is pixel-identical to the one from 15d44e0. Dark and Legacy are independently authored theme alternatives (`plugins/rvox/Theme.hpp`). They are not measured against, or claimed to match, any original dark or legacy skin pixels. Choosing a skin recolours only that editor and stores it as the default for editors opened later, including new instances (`userApplicationDataDirectory/Tsunami/RVox/skin.txt`, read and written on the message thread only). Editors that are already open keep their skin. The skin is not plugin state: no parameter, APVTS or state-format change. rvox.editor checks 100 to 105 cover the selector items, accessible title, keyboard focus, header placement and readable selector text. They check readout and caption contrast of at least 4.5:1 in all three skins and that value entry and host automation still work. A switch back to Light restores the snapshot pixel-exactly. State, parameters and gate/comp gestures are unchanged, and audio through 24 blocks of skin switches is bit-identical to an editor-less twin. Checks 106 to 110 cover persistence, using a temporary preference file, never the real user one. Clean install opens Light and an opened editor writes nothing. The choice is stored, a new instance and a reopened editor open with it, and other open editors are not changed. Malformed, empty, multi-line or oversized files and an unreadable path fall back to Light. An unwritable path keeps the choice in the current editor. There is still no WaveSystem toolbar, so no preset bar, undo/redo, A/B or toolbar menu. These are component events under xvfb, not native-peer input or a hosted DAW. |
| Mono and stereo components | **partial** | One product offers stereo and opt-in mono 1-in/1-out. Mono is bit-identical to the 1-channel core, with state, meters and layout refusal covered by rvox.adapter checks 60-70. There is no separate "RVox Mono" component name. |
| Ranges: Comp -36..0, Gain -36..0, Gate -inf..0, Output meters -inf..0 | **present / partial** | Comp and Gain match. Gate uses a -80 dB finite sentinel for -inf. The guide's printed "Range: -36 dB to -36 dB" is a typo in the guide, so ranges come from parameters.json and the 17.1 resources. |
| Display resolution of 0.1 dB | **present** | Readouts show one decimal, matching `reference_display_step_db` 0.1. |

## Not covered

- No pixel or visual-equivalence comparison against an original-host screenshot. Only the guide image was viewed. It is a different skin capture at a different scale, so it was not compared numerically.
- Skins: no hosted (pluginval/DAW) screenshot of Dark or Legacy yet. Only Linux xvfb component snapshots were reviewed. A hosted capture shows whatever skin was last chosen on that machine (Light on a clean CI runner). `rvox.adapter` opens an editor without redirecting the preference, so it reads the real per-user `skin.txt` (it never writes it). The skin file read is capped at 64 bytes, but a named pipe placed at that path would still block opening the editor.
- Windows hosted editor screenshot: the Windows CI job opens the editor (`host_smoke.py --capture`), but its artifact was not reviewed here.
- Linux CI does not capture the editor yet. This capture was made locally.
